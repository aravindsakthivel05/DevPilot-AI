# Evaluation data

The separate [`training-repository-catalog.json`](training-repository-catalog.json) lists the 15
repositories grouped in `testreposlink.docx`. Their locally indexed, pinned snapshots are recorded
in [`training-repository-snapshots.json`](training-repository-snapshots.json). Seven snapshots were
newly added; 175 source-linked candidate cards for those repositories are in
[`review-queue-testrepos/`](review-queue-testrepos/). These cards are pending source-review, not
scored data. A separate local QLoRA experiment uses only tree metadata to practice transferable
repository-structure reasoning; it does not learn source contents. Its data and measurements are
in [`transfer-training/`](transfer-training/), and the current adapter failed the held-out transfer
check, so it is not enabled in DevPilot. Repository indexing remains the mechanism for retrieving
exact facts about a particular repository. See the [reviewed learning workflow](../docs/learning-loop.md)
before promoting any review card.

`cases.jsonl` contains one reviewed question per line. Each record has a stable ID, repository key,
split, question, expected qualified symbols, answerability flag, and review status. The `holdout`
split contains Rich and Spring Petclinic, one Python and one Java repository. These repositories
were inspected during earlier retrieval development, so this split is a reproducible regression
check rather than a clean statistical holdout. A new, independently labelled holdout is needed
before claiming general accuracy.

`clean-holdout-snapshots.json` pins Click and JUnit 4 as a new Python/Java holdout selected
before the next retrieval or prompt tuning pass. These snapshots must not be used to choose
weights, prompts, or models. `clean-holdout-cases.jsonl` contains 12 source-reviewed symbol
questions with source locations. This small sample is only an initial holdout smoke check; it
does not establish general accuracy or cover unanswerable and multi-symbol questions. The old
Rich/Petclinic split remains a regression check. Run the clean set only at a final checkpoint:
`python -m scripts.evaluate_dataset --dataset evaluation/clean-holdout-cases.jsonl --manifest
evaluation/clean-holdout-snapshots.json`.

`final-holdout-snapshots.json` pins urllib3 and Apache Commons Collections at new Python/Java
commits before any questions or model tuning on them. Keep this pair untouched while building
development labels. Write and independently review realistic cross-file and unanswerable
questions before running a final evaluation. A source commit alone is not a scored holdout.

Run `python -m scripts.evaluate_dataset` from the project root. It requires the eight persistent
snapshots listed in `docs/indexed-reference-repositories.json` and rejects missing or changed
fingerprints. It reports recall@8 and mean reciprocal rank. The initial 24 questions are a seed
set; a larger reviewed dataset is needed before claiming general accuracy.

Answer review is separate from symbol retrieval. With a local model configured, run
`python -m scripts.review_answers prepare --output evaluation/answer-review.jsonl` to produce
answers, source locations, and empty human review fields. It refuses to overwrite an existing
file. For each record, inspect the pinned source and set `answer_correct`,
`all_claims_supported`, and `appropriate_abstention` to true or false, explaining uncertain
judgments in `notes`. `all_claims_supported` means every factual repository claim is backed by
the cited source, not merely that a citation marker exists. On answerable questions,
`appropriate_abstention` means the answer did not unnecessarily refuse; on unanswerable ones,
it means the answer expressed the missing evidence instead of guessing. Run
`python -m scripts.review_answers score evaluation/answer-review.jsonl` only after every field
is reviewed. The scorer rejects incomplete reviews and reports correctness and support both
across all cases and on generated answers only, so a location fallback cannot inflate a
generated-answer support rate. Generated answer files are artifacts, not
gold labels, and should not be used to train a model without independent review.

`cases-v2.jsonl` adds eight explicit live/private/future-state questions to the original 24
symbol questions. These are excluded from symbol-retrieval averages and are for abstention
evaluation. `python -m scripts.review_answers prepare --dataset evaluation/cases-v2.jsonl
--only-unanswerable --output evaluation/unanswerable-review.jsonl` prepares that subset.
The current deterministic guard covers only explicit external-state wording. The 8/8 reviewed
check in `unanswerable-postguard.jsonl` is a narrow contract test, not a general hallucination
rate or a substitute for diverse unanswerable questions.

`review-queue/` contains 25 source-linked candidates per original repository,
generated by `scripts.seed_review_queue`. The queue spreads candidates across non-test files
and includes a source excerpt so a reviewer can write a realistic question and expected answer.
Its blank questions are not evaluation data; do not change `review_status` to `reviewed` without
checking the full pinned source and the proposed answer. Add independently written negative and
cross-file questions as well. The queue generator refuses to overwrite existing edits. Once
cards are completed, `python -m scripts.promote_reviewed_questions --manifest
evaluation/reference-snapshots-v1.json --base evaluation/expanded-cases-v3.jsonl --output
evaluation/expanded-cases-v4.jsonl` promotes only reviewed cards,
verifies their pinned symbols, and refuses to overwrite the result. It does not infer that a
blank or automatically seeded question has been reviewed.
Forty cards have been source-reviewed and promoted into `expanded-cases-v3.jsonl`; 160 remain
pending. The new questions were seeded from known symbols, so further independent cross-file
questions are needed to avoid an overly easy retrieval test.

`workflow-cases.jsonl` is a separate four-question development probe written around multi-stage
behaviour, with multiple source-reviewed expected symbols per question. Its recall@8 is the
fraction of all expected symbols retrieved, not simply whether one symbol was found. Keep it
separate from the symbol-seeded set when diagnosing retrieval; four cases are not an accuracy
estimate. Its case-level output is `workflow-retrieval.json`.

The opt-in LangGraph path has a [separate design and measurement note](../docs/langgraph.md).
`scripts.evaluate_agent_investigation` compares complete evidence-only quick and deep answers
without model calls. The `langgraph-*-response-checkpoint.json` files are the comparable final
measurements. Earlier `langgraph-*-development*.json` files include unsuccessful merge-rule
trials and timed quick retrieval alone, so their latency numbers should not be compared with
the response checkpoints. None of these retrieval scores establishes generated-answer correctness.

`pydantic-test-candidates.jsonl` pins three easy/medium/hard Python questions to a specific
Pydantic commit before running DevPilot. `pydantic-devpilot-question-run.json` records the initial
Llama run; later versioned artifacts preserve each rerun. The latest
`pydantic-devpilot-question-run-v14.json` records the latest run of the same Quick/Deep questions
after schema-constrained generation, separate aspect checks, and deterministic source-line
selection. The [manual source review](../docs/pydantic-question-test.md) separates
retrieved-symbol recall from generated-answer completeness and records that its relevance checks
do not establish semantic entailment.

The [public repository tier test](public-repository-tier-test.md) runs local Qwen answers through
both Quick and LangGraph Deep on FastAPI, Django, and a scoped PyTorch snapshot. It reports
retrieval recall separately from citation-format checks and manual answer review; its three
questions are diagnostic examples, not a general accuracy estimate.
